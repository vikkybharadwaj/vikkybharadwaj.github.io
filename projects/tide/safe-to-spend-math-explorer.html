The end-to-end formula

Spendable Balance − Upcoming Bills − Credit Card Debt + Expected Incomescoped to the until-payday window
↓ = Runway
Runway ÷ daysUntilPaydayhow many days until your next paycheck lands
↓ = Daily Budget
Daily Budget × daysInWindow[tab]where daysInWindow varies per tab (Today=1, Week=N, Month=M, Payday=daysUntilPayday)
↓ = Tab amount
Runway − Typical Discretionary[tab]CONTEXT: not part of the runway formula. Surfaced as projection-at-windowEnd.
↓ = You’d likely have $X left by {windowEnd}

The components — click any card to drill in

+
Spendable Balance Cash in checking + savings, right now

What it is

Sum of your active checking accounts only, using availableBalance when Plaid provides it (subtracts pending debits automatically) and falling back to currentBalance when not. Savings, money-market, HSA, and CD balances are deliberately excluded from runway and surfaced separately in the “Set aside in savings” row (v4.9 behavioral choice — money you've moved to savings shouldn't feel spendable).

Filters

  • account_type = 'depository' AND account_subtype = 'checking'
  • is_active = true
  • Other depository subtypes (savings, money market, HSA, CD) → surfaced as setAsideAccounts[] for transparency, but NOT included in runway

Time semantics

Snapshot — same value across all tabs. Spendable balance doesn’t change based on which timeframe you’re looking at. It’s “cash you have right now.”

Code reference

safe_to_spend_service.ts (v4.9)
const checkingAccounts = allAccounts.filter(
  a => a.accountType === 'depository' && a.accountSubtype === 'checking'
)
const setAsideDepositoryAccounts = allAccounts.filter(
  a => a.accountType === 'depository' && a.accountSubtype !== 'checking'
)
const spendableBalance = checkingAccounts.reduce(
  (sum, a) => sum + (Number(a.availableBalance) || Number(a.currentBalance) || 0),
  0
)

User 53 example

3 checking accounts, 0 savings. Total checking: BofA $7,316.47 (availableBalance after $4K pending debit) + Adv Plus $0.01 + Wells Fargo Everyday $2,514.68 = $9,831.16. setAsideAccounts = []. If you opened a $5K savings, it would surface in the “Set aside” row but NOT add $5K to your spendable balance.

−
Upcoming Bills Recurring outflows due in the window

What it is

Sum of predictedNextAmount for every recurring_streams row of type bill or subscription with confidence ≥ 0.3 whose predictedNextDate falls inside the current tab’s window.

Filters

  • stream_type IN ('bill', 'subscription')
  • is_active = true
  • confidence_score ≥ 0.3 (anything below is shown as possibleBills but NOT subtracted from runway)
  • predicted_next_date ≤ tab’s windowEnd

Time semantics

Window-scoped per tab. The set of bills shrinks/grows depending on which tab you’re on. The runway uses the until-payday-scoped bills (because runway is anchored to payday). Other tabs use their own window for the “Also coming up in this window” context section.

User 53 example (until-payday window, payday May 1)

LA Fitness $10.66 (Apr 24) + Amazon Prime $3.19 (Apr 26) = $13.85 total. Mortgage $3,339.92 (May 2) is OUTSIDE the until-payday window (May 1 is payday, May 2 is the day after) so it doesn’t count.

Code reference

safe_to_spend_service.ts (computeWindow)
const windowBills = billStreams.filter(
  (s) => isInWindow(s.predictedNextDate, windowEnd)
)
// then sum predicted_next_amount for confidence ≥ 0.3
−
Credit Card Debt Total owed across all CC accounts

What it is

Sum of |currentBalance| across every active credit card account. This is the full outstanding debt, not just the statement balance or minimum payment.

Filters

  • account_type = 'credit'
  • is_active = true

What it includes (important)

  • Last cycle’s statement balance (the amount due by your next statement date)
  • This cycle’s spending so far (will appear on next month’s statement)
  • Any pending charges that have already posted to the card

Plaid’s currentBalance updates within minutes of every swipe.

Why we treat the full balance as immediately due

Most conservative interpretation. Treating only the minimum payable (~2-3% of balance) would balloon runway and structurally encourage carrying balances + paying interest. Treating only the current statement balance would require Plaid’s Liabilities product (we don’t use it yet) or detecting statement cycles from transaction history.

Behavioral effect

When you swipe $50 on CC at lunch, your CC balance goes up $50 → next API refresh shows runway $50 lower. You see the cost today even though you won’t physically pay until next month. That’s the intended discipline — you can’t escape the math by switching from debit to credit.

Time semantics

Snapshot — same value across all tabs. Like Spendable Balance, this is “debt right now,” not anchored to any window.

User 53 example

Ultimate Rewards $4,435.68 + Prime Visa $2,128.85 + United Explorer $0 + Free Spirit $0 + WF Active Cash $456.98 = $7,021.51

Open question

For users whose CC due date falls between paydays (biweekly, semi-monthly), the “all CC debt is immediately due” assumption is too conservative. See Open Questions section below.

Code reference

safe_to_spend_service.ts
const creditCardDebt = creditAccounts.reduce(
  (sum, a) => sum + Math.abs(Number(a.currentBalance) || 0),
  0
)
+
Expected Income Recurring inflows in the window

What it is

Sum of predictedNextAmount for income streams with confidence ≥ 0.75 whose predictedNextDate falls inside the window.

Filters

  • stream_type = 'income'
  • is_active = true
  • confidence_score ≥ 0.75 — stricter than the bill bar. The 0.85 narrative bar (used in Smart Pulse / Morning Brief copy) stays at 0.85 to avoid describing gig income as guaranteed; the 0.75 math bar is scoped to SafeToSpend so the runway formula counts it.
  • predicted_next_date ≤ tab’s windowEnd

Time semantics

Window-scoped per tab, like Upcoming Bills. The runway uses the until-payday window.

Threshold philosophy

Income confidence is gated harder than bill confidence because over-counting income is more dangerous than under-counting bills. If we add phantom income to runway, the user spends more aggressively than they should.

User 53 example

primary employer payroll confirmed via “Confirm your paycheck” UX → flagged with user_confirmed=true. Single observation though, so confidence stays low → predictedAmount is null. Net expected income for the window: $0.

÷
Daily Budget Runway divided by days until payday

What it is

The pay-cycle daily-rate. dailyBudget = runway / daysUntilPayday. On payday-today (daysUntilPayday = 0), it collapses to runway itself (one-day window).

Why this is a thing

Earlier versions tried to compute per-tab amounts as spendable + scopedIncome − scopedBills − ccDebt. Side effect: in mid-week with no bills, “This Week” collapsed to the same number as “Until Payday.” Switching to dailyBudget × daysInWindow gave a uniform daily rate everywhere. (See SafeToSpend v4.1 / v4.2 in the version history.)

Time semantics

Anchored to payday — single value across all tabs. The daily rate is the same whether you’re on Today or This Month; what changes per tab is how many days you multiply it by.

User 53 example (payday May 1, daysUntilPayday=8)

runway $6,795.80 ÷ 8 days = $849.48/day

×
Tab Amount Daily budget × days in this tab’s window

What it is

The big number on the SafeToSpend hero card. amount = dailyBudget × daysInWindow for all four tabs (with the until-payday tab equaling runway by construction).

Per-tab daysInWindow

  • Today: 1 day
  • This Week: from today through end of ISO week (Mon-Sun) in user’s timezone
  • This Month: from today through end of calendar month in user’s timezone
  • Until Payday: from today through resolved nextPayday in user’s timezone

Note

When This Month extends past next payday (e.g., 9-day window when payday is 8 days away), a footnote appears: “Extends N days past your next payday — this projection assumes the same daily rate continues.”

User 53 example

Today        = $849.48 × 1   = $849.48
This Week    = $849.48 × 4   = $3,397.92  (today through Sun Apr 26)
This Month   = $849.48 × 8   = $6,795.84  (today through Wed Apr 30 — same as runway)
Until Payday = $849.48 × 8   = $6,795.84  (today through Fri May 1 — same as runway by construction)
~
Typical Discretionary CONTEXT — projection of future non-recurring spend

What it is

Forecast of how much you’ll spend on NON-RECURRING purchases (across both checking and credit card outflows) between today and each tab’s windowEnd, based on your last year of transaction history. Robust mean per day-of-week capped at the 90th percentile.

Why it’s context, not a runway input

Future impulse spending is genuinely volatile per-week. Subtracting a guess from runway would create a confusing “the app is eating my runway” feeling. So we surface it separately as “Projection at {windowEnd}” — a projection, not a commitment.

Per-tab

The forecast SUM differs per tab (different windowEnds), but the underlying weekday averages are user-level (computed once over the full lookback).

How the math changes per tab

Same underlying components — different window scopes. Spendable balance, credit card debt, and daily budget are tab-invariant; bills, income, and typical-discretionary all re-scope to the tab’s window.

Worked example — user 53, apr 23 2026

Setting: payday May 1 (semimonthly variant 1st & 15th, 8 days away), 3 checking accounts, 5 CC accounts, 1 confirmed primary employer paycheck (low confidence).

spendableBalance = $13,831.16     (Bank of America + Adv Plus + Wells Fargo Everyday)
upcomingBills    = $13.85         (LA Fitness Apr 24 + Amazon Prime Apr 26)
creditCardDebt   = $7,021.51      (Ultimate Rewards + Prime Visa + WF Active Cash; United and Free Spirit are $0)
expectedIncome   = $0             (primary income stream too low conf to count amount yet)

runway          = 13,831.16 − 13.85 − 7,021.51 + 0 = $6,795.80
dailyBudget     = 6,795.80 ÷ 8 days                = $849.48/day

Today      = 849.48 × 1 = $849.48     (Apr 23, 1 day)
This Week  = 849.48 × 4 = $3,397.92   (Apr 23 → Apr 26, 4 days)
This Month = 849.48 × 8 = $6,795.84   (Apr 23 → Apr 30, 8 days)
Until Pay  = 849.48 × 8 = $6,795.84   (Apr 23 → May 1, 8 days; equals runway)

Open questions / known simplifications / planned features

  • Plaid Liabilities for CC due-date splitting. Today we treat all CC debt as immediately payable, which over-tanks runway right after a statement closes (you just got a $5K bill — runway drops $5K — even though due date is 25 days away). With Plaid Liabilities (separate product, we have production access) we'd get last_statement_balance + next_payment_due_date per card, and could split the CC line into "Due [date]" + "Accumulating for next cycle". Total subtracted stays the same; clarity goes way up. Same product unlocks: per-card due-date alerts, minimum-payment safety nudges, APR-aware "you're carrying balance at 24%" warnings, missed-payment detection.
  • Apple Card-style payment simulator. Future feature concept (paired with Liabilities) — slider/wheel UX showing how 25% / 50% / 75% / 100% CC payment translates to interest charged. Apple Card's wheel is the reference design.
  • Plaid Signal for live spend pressure. Today's runway drop after a swipe is delayed by the Plaid sync chain (bank → Plaid → us → mobile). Pending charges appear within minutes-to-hours typically; posted charges lag 1–3 days. Plaid Signal is a separate product that targets near-real-time spend tracking. Worth investigating once we want to close the "user could overspend before runway updates" gap.
  • Detector coverage gap on recurring streams. The recurrence detector typically needs ≥3 occurrences to confidently classify a pattern. Side effect: real recurring stuff with thin history gets misclassified as discretionary. User 53's BILT CARD HOUSING (rent, ~$4,200/mo) has only 2 occurrences in 102 days of data — so it's not detected as a recurring bill, and its $4,200 lands in “typical discretionary” instead, inflating the Thursday weekday average from ~$15 to $666. Fix: a parallel "Confirm a recurring bill" UX (mirror of the existing "Confirm your paycheck" pattern) — user taps a transaction → flagged with user_confirmed=true on a recurring_streams row → bypasses the detector's occurrence-count threshold. Also covers: new users (<3 months data), irregular cadence (quarterly insurance), first-occurrence bills (just-started gym).
  • Lookback bump from 365 → 730 days. Plaid gives us 2 years; we currently cap at 365 conservatively. Once users approach 1 year of history, bump LOOKBACK_DAYS_MAX = 730. One-line change. Note: month-of-year seasonality (December holiday, summer travel) needs 3+ years to denoise reliably — not solvable yet even with 2-year lookback.
  • Today's typical-discretionary doesn't subtract today's already-completed swipes. If your Thursday typical is $666 and you've already spent $50 by lunch, the projection still treats today as a fresh $666 day. Errs conservative. Could be tightened to project "remaining today" instead.
  • Statement balance vs total balance for CC subtraction. We use total currentBalance, which over-counts current-cycle swipes (those have grace before they're owed). Most cashflow apps default to this conservative read. Resolved by the Liabilities-based split above.
  • Minimum payment vs full balance. We treat full balance as "owed." Showing only the min payable would balloon runway by ~97% and structurally encourage carrying balances + paying interest. Deliberate behavioral choice — we don't want to be that app.
  • Savings deliberately excluded from spendable balance. v4.9 — savings, money-market, HSA, CD subtypes don't count toward Safe to Spend. Surfaced as setAsideAccounts in a separate row labeled "Set aside in savings." Encourages users to keep savings savings.
  • Loan accounts are excluded from runway entirely. Plaid doesn't reliably surface loan transactions; mortgage isn't the kind of debt you pay off next month anyway. Surfaced as loansExcluded[] for transparency.
