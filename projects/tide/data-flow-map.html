Dashboard Load Flow (MVP)
Home screen assembly in a single request. One controller handler fans out four parallel Lucid queries and returns the aggregated payload. Target: under 500ms end-to-end. The Home screen itself then issues a small number of follow-up GETs (SafeToSpend, Bills) in parallel — each of those is its own flow in this map.
1Mobile App
User opens the app / pulls to refresh on Home
Home screen mounts. In dev mode SKIP_AUTH=true in apps/mobile/app/_layout.tsx bypasses onboarding and routes straight to (tabs)/home. Default user is dev-bypass user ID 53 (all data belongs to this user in dev).
2Mobile App
Sends GET /api/dashboard with Cognito access token
Axios instance injects Authorization: Bearer {access_token} from Expo SecureStore. If the token is expired (>1h old), a 401 interceptor refreshes via the 30-day refresh token transparently before retrying the request. Dev mode skips logout() on 401 so the auth cache isn't wiped during local work.
3Backend API
JWT validation via aws-jwt-verify in auth_middleware
Validates signature, audience, expiry against Cognito JWKS (cached). Extracts cognito_sub and resolves to internal users row. Dev bypass: when NODE_ENV !== 'production', middleware short-circuits to user ID 53 regardless of token — ensures dev data stays consistent for a single user.
~5ms (cached JWKS)
4UsersController
Routes GET /api/dashboard → UsersController.dashboard()
File: apps/backend/app/controllers/users_controller.ts:114-145. Handler authenticates via Adonis auth.user!, then fans out a single Promise.all() with three independent queries (accounts, transactions, bills). All three run concurrently — the slowest one determines total latency.
5aLucid ORM
Query 1: active bank accounts
BankAccount.query().where('userId', user.id).where('isActive', true). Returns depository, credit, and loan rows. Each row includes availableBalance, currentBalance, accountType, accountSubtype, mask, encrypted officialName (auto-decrypted by Lucid computed property).
~15-40ms
5bLucid ORM
Query 2: last 10 transactions
Transaction.query().where('userId', user.id).orderBy('transactionDate', 'desc').preload('merchant').preload('category').limit(10). Preloads nested merchant + category rows so the mobile side has display name, icon, and color in one payload. Recent-transactions list on Home renders from this directly.
~20-80ms
5cLucid ORM
Query 3: upcoming bills (next 5)
RecurringStream.query().where('userId', user.id).where('isActive', true).whereIn('streamType', ['bill','subscription']).where('predictedNextDate', '>=', today).orderBy('predictedNextDate', 'asc').preload('bankAccount').limit(5). Reads directly from recurring_streams (the sole source of truth as of 2026-04-22). Rows are mapped to a slim shape so the dashboard field matches what the Bill Predictions flow returns from GET /predictions/bills.
~10-30ms
6UsersController
Aggregates and serializes response
totalBalance = accounts.reduce((sum, a) => sum + a.availableBalance, 0). Final JSON: { totalBalance, accountCount, accounts[], recentTransactions[], upcomingBills[] }. toJSON() invokes Lucid's serialization: encrypted fields decrypted automatically; fields marked serializeAs: null (SSN, Plaid access_token, etc.) are excluded from the wire payload.
7Mobile App
Renders Home shell and fires follow-up GETs in parallel
React Query caches dashboard payload under ['dashboard'] with 60s staleTime. Home immediately issues parallel follow-ups for the features that have their own endpoints: GET /predictions/safe-to-spend?timezone=… (SafeToSpend), GET /predictions/bills (Upcoming Bills — streams-based source of truth). Each of those is its own spec on this page.
8Mobile App
Composes final Home UI in the canonical order
Render order on Home: SafeToSpend (with 4-tab segmented control, default Until Payday) → Recent Transactions (top 10 from this dashboard call) → Upcoming Bills (top 5 from streams). Pull-to-refresh re-runs step 1 and invalidates all three React Query caches.
Total end-to-end: ~300-500ms
SPEC — DASHBOARD
Endpoint contract
GET /api/dashboard → { totalBalance: number, accountCount: number, accounts: BankAccount[], recentTransactions: Transaction[10], upcomingBills: UpcomingBill[5] }. Auth required. Bouncer policies enforce user_id === authenticatedUserId on every preloaded relation. upcomingBills[] items carry { id, predictedAmount, predictedDate, confidence, recurrencePattern, merchant: { name }, accountName, accountType } — same shape as GET /predictions/bills so mobile can use one component. No pagination — the limits are hard-coded (10 transactions, 5 bills) because this is a home screen summary.
Parallelism & budget
One Promise.all() over three queries. Target p95 < 500ms. If any single query exceeds ~200ms we treat it as an N+1 or missing-index bug, not a design tradeoff. Home makes 3 parallel follow-ups after this call (SafeToSpend, Bills, and the notifications inbox badge) — all run off the same auth middleware cache so JWT re-verification is <1ms.
Render order on Home (canonical)
1. SafeToSpend (4-tab control, default Until Payday) — see Safe to Spend Flow
2. Recent Transactions (top 10 from this dashboard call, tap row → transaction detail)
3. Recurring Expenses (v5.2 — account-scope pills [Checking & debit | Credit cards], dated list with category chips; depository view includes display-only card-payment rows badged "in Safe to Spend"; credit view is display-only card-billed recurring spend with explainer) — see Bill Predictions Flow
Security invariants
• All four queries filter on user_id = auth.user.id. Never trust query params for user scope.
• Encrypted account fields (officialName, mask) auto-decrypt via Lucid computed properties. Plaid access tokens never leave the backend (serializeAs: null).
• Logs use redactForLogging() — no PII in CloudWatch.
Transaction Sync Flow (MVP)
Daily 2 AM CST cron job syncs the last 30 days of transactions for all active bank connections (v5.3 — was 7; the pull is a stateless transactions/get date range with NO cursor, so a late-posting transaction or a multi-day outage fell out of the 7-day window forever while newer rows kept landing. The field case: a May 29 payroll deposit missing while June 4/8 synced fine. Dedup on plaid_transaction_id makes the wider re-pull idempotent; cursor-based /transactions/sync is the eventual fix). Transactions land with their category_id assigned per the Plaid Sync Category Resolution Priority (see the block below). Also triggered by pull-to-refresh and Plaid webhooks.

Triggers at 2:00 AM CST daily
BullMQ repeatable job. Queries all active bank_connections.

Enqueues SyncDailyTransactionsJob per connection

Circuit breaker: 5 failures → open 30s. Retry: 3 attempts with 2s/4s/8s backoff. Timeout: 10s.
~200-500ms per call
4aWorker
Upserts merchants
Keyed by plaid_merchant_id when available, else by name. Stores Plaid primary/detailed codes on merchants row.

User-set categories are NEVER clobbered on re-sync (invariant). Also stores pending_transaction_id from Plaid so the pending-dedup filter can fire later at read time.

PLAID SYNC — CATEGORY RESOLUTION PRIORITY
For each incoming transaction, category_id is resolved by walking three tiers in order. The first tier that produces a non-null category wins. Applied in step 4c above.
TIER 1
User Override
merchant_category_overrides row — hand-set by the user on a prior transaction via the "change category" flow (backend support exists; mobile UI is MVP+). Applies to ALL future transactions from that merchant for that user. categorySource='user'. Never clobbered on re-sync — this is the invariant that makes user corrections stick.
TIER 2
Merchant AI Cache
merchants.ai_category_id — set by Claude Haiku on a prior sync when Plaid's code was ambiguous (step 4b). categorySource='ai'. One AI call per unique merchant, reused forever. Ambiguous Plaid codes today: GENERAL_SERVICES_OTHER, ENTERTAINMENT_OTHER, PERSONAL_CARE_OTHER, GENERAL_MERCHANDISE_GIFTS_AND_NOVELTIES, null. Widen this set based on DB evidence — not blind speculation.
TIER 3
Plaid Detailed Code
Plaid's native PFC classification. categorySource='plaid'. Handles confident cases (coffee, gas, groceries) with zero AI cost. Used when no user override and no AI cache.
Related: See Spending Insights Flow for how categorized transactions are aggregated into the donut + category list. The same priority chain is visualized on the AI Pipeline page for the AI-first view of the system.
AI Coach Flow (MVP)
Input-first chat UI with suggestion chips. User types → createChat → navigate with initialMessage → auto-send via useEffect → SSE stream via XMLHttpRequest → Tide Coach tool loop over AWS Bedrock (Claude Sonnet 4) → persist both messages via BullMQ. Multi-turn, tool-using, with a strict alternating-role contract that Bedrock requires and this flow enforces.
1User
Types a message or taps a suggestion chip on AI Coach tab
Input-first design. Suggestion chips cover the common jobs: "How much can I spend this week?" / "Why is my dining so high?" / "What bills are coming up?". Hamburger drawer shows chat history with swipe-to-delete. New-chat button clears the thread.
2Mobile App
POST /api/chats to create the chat row, then router.push with initialMessage
createChat returns { id }. App navigates to /chat/[id] with the first message as a URL param. Chat screen's useEffect on mount reads initialMessage and fires sendMessage exactly once — same path as any subsequent user turn. This unifies "first message" and "nth message" into one code path.
3Mobile App
Opens SSE stream via XMLHttpRequest (not fetch)
React Native's fetch() does NOT expose response.body as a ReadableStream — so streaming via fetch is impossible. apps/mobile/src/services/sse-client.ts uses XMLHttpRequest with onprogress to read incremental bytes, parses event:/data: lines, and re-emits events as they arrive. This is load-bearing — see LEARNINGS.md "Streaming not supported".
4ChatsController
POST /api/chats/:id/messages → ChatsController.sendMessage()
File: apps/backend/app/controllers/chats_controller.ts:76-291. Bouncer: ChatPolicy.edit(chat) enforces ownership. Validator: sendMessageValidator (non-empty content). If isBedrockAvailable() returns false (missing AWS creds), returns 503. First turn also sets chat.title to the first 100 chars of the user message.
5ChatsController
Persists the user message SYNCHRONOUSLY before loading history
The user message is written to chat_messages via ChatMessage.create() — NOT queued. Why: the next turn's history query would otherwise see two consecutive user roles because the queued assistant response from this turn isn't persisted yet. Content is AES-256 encrypted at rest. Role = 'user'.
6ChatsController
Loads chat history and builds Bedrock message array
Query: last chatConfig.maxContextMessages messages for this chat (default 20, covers ~10 turns). Reverses to chronological. Decrypts each with getDecryptedContent(). Filters out blank messages — Bedrock's ConverseStream API rejects empty text ContentBlocks, which caused a multi-turn crash (see LEARNINGS.md 2026-04-18).
7ChatsController
Enforces strict alternating user/assistant roles
Bedrock's Converse API REJECTS consecutive same-role messages. Cleanup loop: (a) if two consecutive user messages (queue lag dropped the assistant reply), keep the later one; (b) if two consecutive assistant messages, keep the first; (c) strip leading non-user messages so conversation starts with 'user'. This is defensive — the synchronous user persistence in step 5 usually prevents the issue, but the queue fallback path can still produce gaps.
8Intent Classifier
(Disabled) Claude Haiku 4.5 intent classification
const intentPromise = Promise.resolve('unknown'). Intent classification is currently turned OFF — it consumed a separate Haiku call per message and competed with the chat stream for Bedrock quota, causing throttle errors during multi-turn sessions (see commit 32cd3ad). Re-enable once AWS quota is raised. The persistence path still writes intentClassified to chat_messages for future filtering.
9ChatsController
Opens SSE response headers and starts streaming
Content-Type: text/event-stream, Cache-Control: no-cache, Connection: keep-alive, X-Accel-Buffering: no (prevents nginx/CDN buffering). Local sendSSE(event, data) helper writes event: X\ndata: JSON\n\n frames. Builds system prompt via buildCoachSystemPrompt(user.fullName) and instantiates new ToolExecutor(user.id) against a read-only DB connection.
10BedrockService
streamCoachResponse — Converse loop with tool use
Model: us.anthropic.claude-sonnet-4-20250514-v1:0 (Tide Coach). Tool loop: max MAX_TOOL_ITERATIONS = 10 iterations. Each iteration: Bedrock streams text chunks + possibly a tool use block; controller relays text to SSE as event: text_delta; if the model requests a tool, controller pauses, runs it via ToolExecutor, feeds the result back into the next Converse round. Throttle handling: ThrottlingException triggers exponential backoff retry (1s/2s/4s).
First token < 2s
11ToolExecutor
Executes Tide Coach tools against read-only DB
11 tools available (see AI Pipeline page for the full list). Headliners: calculate_safe_to_spend (delegates to shared safe_to_spend_service.ts — same numbers as the SafeToSpend card), get_spending_by_category, query_transactions, query_bills_predictions, query_payday_predictions. F0.1 / Epic 0 (2026-06): calculate_safe_to_spend's result is shaped by the pure projectSafeToSpendForCoach() projection so it surfaces EVERY field the Home card renders — per-window bills[]/income[], the full resolved payday envelope, the accountsIncluded/setAsideAccounts/creditCards/loansExcluded arrays, lastSyncedAt, and typicalDiscretionary.perDayOfWeek. The Coach answers "which bill is due first?" or "which account has the most?" without a second tool call. Each tool call runs with Bouncer policies enforced on the read-only connection. Tool input/output appended to accumulatedTools for persistence. Each tool call is emitted as event: tool_use over SSE so mobile can render a "thinking about X" chip.
~30-200ms per tool
12Mobile App
Renders streaming tokens + tool chips in chat UI
Tokens append to the in-flight assistant bubble character-by-character as event: text_delta frames arrive. Tool use frames render as small chips ("Checking your spending…"). On event: done the bubble freezes. On network drop or malformed frame, the client keeps whatever partial text it has rather than erasing — mirrors server-side partial persistence.
13ChatsController
Persists the assistant message via BullMQ (with synchronous fallback)
persistAssistantMessage(accumulatedText, accumulatedTools) dispatches PersistChatMessageJob to queue chat-messages (30-day failure retention — do not reduce). Job writes { chatId, role: 'assistant', content, intentClassified, toolsUsed (JSON), modelUsed: SONNET_MODEL_LABEL } — the label is derived from SONNET_MODEL_ID (strips the us.anthropic. prefix and dated -v1:0 suffix), resolving to 'claude-sonnet-4' — with AES-256 encrypted content. If queue dispatch throws (Redis down), falls back to a synchronous ChatMessage.create(). Both success and error paths call this — partial assistant responses are persisted even when streaming errors out mid-flight.
14ChatsController
Emits event: done and closes the SSE stream
Final frame carries { intent } (the classifier is disabled, so this is 'unknown'). Latency telemetry (totalLatencyMs, firstTokenMs, tool count) is written server-side to the ai_traces table, not sent in the done frame. nodeRes.end() closes the HTTP response. On error path: event: error with a user-facing message, then done, then persist whatever partial text accumulated.
SPEC — AI COACH
Models
Tide Coach (streaming, tool use): us.anthropic.claude-sonnet-4-20250514-v1:0. Intent classifier (disabled today, reserved for quota recovery): us.anthropic.claude-haiku-4-5-20251001-v1:0. Access via AWS Bedrock Converse / ConverseStream APIs. Custom HTTP strategy is used for Bedrock AgentCore JWT auth (AWS SDK cannot — see CLAUDE.md).
Context window
chatConfig.maxContextMessages = 20 (chronological). Blank messages are filtered out before sending to Bedrock (empty text blocks crash ConverseStream). Alternating user/assistant roles enforced — defensive cleanup handles the rare queue-lag gap.
Tool loop
Max MAX_TOOL_ITERATIONS = 10 per turn. All tools run against a read-only DB connection. Bouncer policies still enforced: user_id === authenticatedUserId at every query. calculate_safe_to_spend delegates to the shared safe_to_spend_service.ts — Home card and AI Coach return byte-for-byte identical numbers. Home parity (Epic 0): the tool result is shaped by the pure projectSafeToSpendForCoach() projection so every field the Home card renders is reachable in ONE call (no follow-up tool call, no Coach-side arithmetic); a "Home parity principle" system-prompt rule (F0.2) forbids re-computing these numbers, and the coach_safe_to_spend_parity.spec.ts unit test (F0.4) fails CI if a field is ever dropped.
Streaming transport (React Native quirk)
Mobile client uses XMLHttpRequest + onprogress, not fetch(). RN's fetch does not expose response.body as a ReadableStream. See apps/mobile/src/services/sse-client.ts. Server writes text/event-stream with X-Accel-Buffering: no to disable CDN buffering.
Persistence contract
User message: synchronous write BEFORE history load (invariant for alternating-role contract). Assistant message: BullMQ chat-messages queue with 30-day failure retention (never reduce). Synchronous fallback if queue dispatch fails. Partial responses persisted even on streaming errors.
Throttling & quota
Bedrock ThrottlingException triggers exponential backoff (1s / 2s / 4s) — see commit 2e33ff4. Intent classification was disabled to free quota for the chat stream — re-enable only after AWS quota increase. Circuit breaker on AI service: 5 failures → open 30s. All AI calls use the shared circuit breaker + retry wrapper per CLAUDE.md.
Error paths covered
• Bedrock unavailable → 503 before opening stream
• Throttle → retry w/ backoff, surface only after exhausting attempts
• Streaming error mid-flight → persist partial text, emit event: error + done
• Empty ContentBlock in history → filtered at step 6
• Consecutive same-role messages → cleanup at step 7
• Queue dispatch failure → synchronous DB fallback at step 13
Bill Predictions Flow (MVP)
On-demand recurrence detection. GET /predictions/bills auto-runs the 6-stage RecurrenceDetectionService when streams are stale (>24h) or missing — bypassing any background-job dependency. Streams are persisted to recurring_streams (18 columns incl. predicted_next_amount, predicted_next_date, confidence_score, and the STS v5 category MECE bucket) through the single shared detectAndPersistStreams() path used by all three triggers (on-demand, post-sync, BullMQ job). v5.2 display presentation (presentUpcomingOccurrence, pure + unit-tested): the old predictedNextDate ≥ today SQL bound silently dropped slipped predictions (a stale claude.ai row made an ACTIVE card subscription look "never detected"); now STALE streams (>0.75× period overdue) are SUPPRESSED — never re-asserted — and slipped-but-active dates are ADVANCED into the window via expandOccurrences, marked dateBasis: 'advanced' ("date estimated" in the UI). Consumers: Recurring Expenses card + See All screen (v5.2 — account-scope FilterPills: "Checking & debit" default = depository streams + display-only card-payment rows, counted in STS; "Credit cards" = card-billed recurring charges, DISPLAY-ONLY with an explainer — the card repayment already carries them, so they are never subtracted from Safe to Spend; one shared InfoTip copy map sts-copy.ts keeps the trust copy from forking), Safe to Spend ledger (depository-gated, v5.2), AI Coach query_bills_predictions tool (depository-gated, v5.2).
1Mobile App
Requests GET /predictions/bills?daysAhead=60&limit=25
Home Recurring Expenses card and the dedicated Recurring Expenses screen both hit this. Default daysAhead = 60, limit = 25. Auth token required. React Query caches under ['bills', daysAhead, limit] with 60s staleTime.
2PredictionsController
Freshness check on recurring_streams
File: apps/backend/app/controllers/predictions_controller.ts:17-106. Reads the first active stream for this user. needsRefresh = !existingStreams || (updatedAt older than 24h). If fresh, skip to step 8. If stale or none, run detection in-request (on-demand, NOT background).
~5ms if fresh
3RecurrenceDetectionService
Stage 1 — Normalize merchant descriptions
normalizeDescription() strips: payment processor prefixes (SQ*, PAYPAL*, TST*, SP*), phone numbers (10+ digit runs with punctuation), trailing #codes and REF:codes, corporate suffixes (.COM, INC, LLC, LTD, CORP), and city/state patterns. Result: "NETFLIX.COM #4321 LOS GATOS CA" → "NETFLIX".
4RecurrenceDetectionService
Stage 2 — Fuzzy-match and group transactions
Grouping is ACCOUNT-SCOPED first (v5.3): transactions are partitioned by bank_account_id before any merchant/description matching — the same payer into two accounts is two streams. The field case that forced this: a direct-deposit split lands one employer's payroll into 3 checking accounts on the same days; merged account-agnostic groups produce same-day duplicate intervals (0, 0, 14, 0, 0, 17…) whose CV fails period detection, so the paycheck was never detected at all. Accepted cost: moving a subscription between cards resets its observation count (same class as a renamed descriptor). Within each account: groups by merchant_id when available, else by normalized name; Dice coefficient 0.75 threshold merges near-duplicate names (e.g., "SPOTIFY USA" vs "SPOTIFY"). Each group carries { key, merchantId, normalizedName, transactions[] }. Groups with fewer than 2 transactions are dropped — need at least 2 occurrences to detect recurrence.
5RecurrenceDetectionService
Stage 3 — Detect period from inter-transaction intervals
Sorts each group's transactions by date. Computes median interval in days. Matches against KNOWN_PERIODS: weekly=7 (±2), biweekly=14 (±3), semi_monthly=15 (±3), monthly=30 (±5), quarterly=91 (±10), annual=365 (±20). First period inside tolerance wins. Groups with no matching period are dropped.
6RecurrenceDetectionService
Stage 4 — Compute anchor day + next occurrence
anchorDay = modal day-of-period (e.g., day 1 for monthly rent, day 15 for mid-month). Predicted next date = last observed + detected period, snapped to the anchor day when applicable. averageAmount = mean; lastAmount = most recent; predictedNextAmount = lastAmount (more recent > long-run average for subscriptions that got price hikes).
7RecurrenceDetectionService
Stage 5 — Confidence score + stream type classification
Confidence 0-1 as a weighted sum (computeConfidence): (a) interval regularity 35% (1 − intervalCV/0.5), (b) amount consistency 25% (1 − amountCV/0.3), (c) occurrence count 20% ((count−2)/6, capped at 1), (d) recency 20% (1.0 if last occurrence within 1.5× the detected period, stepping 0.5 → 0.2 → 0 as the gap grows). Streams below MIN_CONFIDENCE = 0.3 are dropped. streamType: positive-amount runs tagged 'income' (paychecks, direct deposits); negative amounts get 'bill' or 'subscription' based on amount stability and merchant name heuristics.
7bRecurrenceDetectionService
Stage 6 — MECE category classification (STS v5)
classifyStreamCategory(): majority vote over the member transactions' Plaid personal_finance_category detailed codes, direction-gated. Debit prefixes: LOAN_PAYMENTS_CREDIT_CARD* → cc_payment, LOAN_PAYMENTS_* → loan, RENT_AND_UTILITIES_* → utility, TRANSFER_OUT_* → planned_savings; credit prefixes: INCOME_* → income, TRANSFER_IN_* → transfer_in. A label wins only with a strict majority of PFC-bearing transactions; otherwise fall back to the legacy cadence heuristic (credit → income; debit <$50 monthly/annual → subscription; else bill). This is the partition that keeps every Money Out dollar in exactly one STS v5 bucket — a checking→card autopay is cc_payment, never a bill.
8RecurrenceDetectionService
Persists via the single shared path detectAndPersistStreams()
One transaction: deactivates detector-owned streams only (user_confirmed streams are never deactivated — a confirmed paycheck with <3 observations must survive every refresh), clears and re-points transactions.recurring_stream_id, then upserts each detected stream by the (userId, normalizedMerchantName, frequency, bankAccountId) composite key (v5.3 — bank_account_id is part of stream IDENTITY, matching the account-scoped grouping and the paycheck-confirmation upsert; without it, two confirmed slices of a multi-account paycheck sharing a normalized name would smear one account's stats onto an arbitrary sibling row) with category. Transactional so concurrent Home calls never observe an all-inactive interim state (would flash resolvePayday() to its fallback mid-render). Same path for all three triggers: this controller, the post-sync background pass, and the BullMQ GeneratePredictionsJob.
9PredictionsController
Reads streams filtered to the Recurring Expenses surface (v5)
where streamType IN ('bill', 'subscription') AND (category IS NULL OR category NOT IN ('cc_payment', 'planned_savings')) AND isActive = true AND predictedNextDate BETWEEN today AND today+daysAhead — card autopays are owned by the STS CC ladder (showing them here would read as a double charge) and planned savings live in the STS breakdown. Loans pass through (their legacy streamType is bill). Response rows carry category + server-computed confidenceBand. Preloads bankAccount for the "Chase • Checking ••4321" label. Sorted by predictedNextDate ASC. Income streams are NOT returned here — they feed Safe to Spend separately.
~10-30ms
10PredictionsController
Shapes the response envelope
Maps each stream to the slim bill shape: { id, userId, merchantId: null, predictedAmount, predictedDate, confidence, predictionConfidence, recurrencePattern, merchant: { name }, accountName, accountType }. Response envelope: { meta: { total, perPage, currentPage, lastPage }, data: […] }. Same shape returned by the dashboard's upcomingBills[] field so mobile uses one component for both.
11Mobile App
Renders the Recurring Expenses UI (v5)

SPEC — BILL PREDICTIONS
Detection pipeline (5 stages)
1. Normalize description (strip processor prefixes, phone numbers, suffixes, city/state).
2. Fuzzy-group by merchant (Dice 0.75). Drop groups with <2 occurrences.
3. Detect period against KNOWN_PERIODS with tolerance bands.
4. Compute anchor day + predicted next amount (uses last, not average, to catch price hikes).
5. Score confidence (35% interval regularity + 25% amount consistency + 20% occurrence count + 20% recency). Drop <0.3.
Periods and tolerances
weekly=7 (±2), biweekly=14 (±3), semi_monthly=15 (±3), monthly=30 (±5), quarterly=91 (±10), annual=365 (±20). First match wins (narrowest tolerance). Tighten bands only with DB evidence — false positives are cheap, missed subscriptions are not.
Thresholds (shared with consumers)
Write-side: MIN_CONFIDENCE = 0.3 (stream must clear this to persist).
Read-side: Recurring Expenses UI shows everything ≥ 0.3 (full list); badges render the server-computed confidenceBand (high ≥ 0.85, medium ≥ 0.5).
Safe to Spend bills: ≥ 0.3 conservative (to avoid overspending).

On-demand refresh at read time when the oldest stream is >24h. No background job dependency — this was an explicit MVP decision. The Transaction Sync flow also enqueues GeneratePredictionsJob after every sync, which refreshes the same streams when the queue worker is running. Either path keeps streams current.

Safe to Spend Flow (MVP — v5.2 ledger, global floor, depository-scoped streams)
v5 daily cash-flow ledger (2026-06-11 rework — 17 locked decisions, PRs #188–#191+): L(d) = spendableBalance + Σinflows(≤d) − Σoutflows(≤d) projected day-by-day from today through max(month end, payday−1), user tz. Tab semantics (v5.1 — the GLOBAL-FLOOR invariant: no window may ever promise money a longer displayed window proves you'll need): every read is bounded by the GLOBAL FLOOR min L(d), d ∈ [today, max(payday−1, month end)]. Pre-v5.1 the week capped at the pre-payday floor while the month projected past payday — a post-payday bill not covered by trusted income made This Week > This Month (the cross-horizon seam, found in the field 2026-06-12); when the awaited paycheck IS confidently detected it is in the ledger and the global floor collapses to the pre-payday floor, so the invariant only bites when post-payday income can't be trusted. Until Payday (default; when no payday is confidently detected — resolved.isFallback — the default tab auto-falls back to Today until the user picks one, mirroring Rocket Money's confidence gate) = the global floor — the most the user can spend now and still cover every projected obligation (the awaited paycheck is never inside its own runway, but an uncovered post-payday bill still caps it). Today = dailyBudget = the sustainable rate min over d of L(d)/daysUntil(d) through the same horizon (spending that rate clears EVERY projected dip, not just the floor day; in a shortfall Today collapses to the floor like every window — a negative per-day rate next to a deeper weekly floor would read as a smaller hole on a shorter tab). This Week = rate × daysInWindow capped at the global floor. This Month = same allocation when month-end ≤ payday−1, else the global floor itself (paychecks land on their dates — income never flat-added before it arrives). The response carries floor {date, value, crossesPayday, bindingBill {label, amount, date} | null} — the binding dip behind every cap; Home's contextual footnote and the Coach narrate it identically ("your balance hits its lowest point around {date} after {bill}"). Known residual seam: obligations just past month end are still invisible; full fix = horizon of next payday + one full cycle (tracked, not shipped). Negative amounts are NEVER clamped — shortfalls ship as first-class shortfall fields. Money Out is a MECE partition (per-window moneyOut): bills/utils/subs (category-gated streams, conf ≥ 0.3) · loans (loan-payment streams; loan account balances stay excluded) · planned savings (own labeled line — still reduces STS) · CC due-this-cycle (per-card ladder: max(0, statement − payments since issue) on the DUE DATE — never the total revolving balance; fallback: detected cc_payment stream "estimated" → minimum payment → explicit ccDueUnknown) · essentials (PFC necessities whitelist, checking-funded only, robust per-weekday mean, cold-start blend min(1, days/60), omitted <14d). All recurring terms are occurrence-expanded (3-paycheck months count 3 paychecks; weekly bills count every week), stale streams (>0.75× period overdue) are suppressed to possibleBills, and projected occurrences matched to a posted/pending transaction within ±4 days are dropped (availableBalance already nets them). Money In: income streams by unified band — high (user-confirmed/declared or ≥0.85) at full amount, medium at p25 "estimated", low excluded. Multi-account paycheck (v5.3): a direct-deposit split is N confirmed slices (one account-scoped stream each) of ONE logical paycheck — every slice lands on the ledger so per-account math stays right, and the payday envelope's predictedAmount is the SUM over slices. Confirmed semi_monthly slices get their occurrence dates from the user's two-anchor pattern via expandSemimonthlyPaydays() (15th + EOM or a day pair, weekend dates rolled back to Friday) — expandOccurrences' single anchorDay steps one month per occurrence and would halve a semimonthly paycheck. A declared Settings amount is the TOTAL per paycheck: it substitutes on the primary confirmed slice and the other confirmed slices are skipped (emitting both would double-count the split). Stream sourcing (v5.2 — depository scoping): outflow, income, and cc_payment streams enter the money math ONLY when sourced from a depository account (or legacy rows with NO account linkage — dropping an unlinked paycheck would be a worse trust failure than the bug this fixes). Credit-card-billed subscriptions/bills are display-only (Recurring Expenses credit view) — checking never pays them directly; they live inside the card’s statement, which the ccDue ladder already subtracts, so counting both was a DOUBLE CHARGE (the field bug: a claude.ai subscription billed to the card was also subtracted from checking). Credit-side "payment received" mirrors that the classifier read as income are never income — that credit is money LEAVING checking, not arriving. Excluded streams land in partitionStreams()’s excludedNonDepository bucket and deliberately do NOT resurface as possibleBills. The gate is ONE shared rule — RecurrenceDetectionService.isMoneyMathEligible() — applied by every money-math consumer: the STS ledger (partitionStreams), payday resolution (resolvePayday primary-stream ranking — a card mirror, often larger than the paycheck, must never BECOME the payday), Coach tools 4/5 (bills + payday predictions), and /predictions/payday upcoming[]. A declared Settings paycheck with no eligible stream to land on is synthesized from the resolved envelope, so it can never silently vanish from the ledger (a card-billed subscription must never come back as a checking "possible bill"). Per-card extras: ccObligations[] (due, basis, APR, total) + ccNextCycleWarning ("$X building toward next statement", escalates when > 50% of expected paycheck). Shared service safe_to_spend_service.ts (pure cores: deriveLedgerTabs() + partitionStreams(), both exported and unit-tested DB-free) — Home and AI Coach calculate_safe_to_spend both delegate, so numbers match byte-for-byte.

2Backend API
Resolves next payday via the canonical resolvePayday() helper
Single source of truth — same helper the AI Coach's query_payday_predictions + calculate_safe_to_spend tools use, so Home and Coach quote the same date. Two cases (STS v5, 2026-06-11): (1) user_setting — user has told us the cadence in Settings (Profile tab → Settings). Monthly uses payday_day_of_month; semi-monthly uses the free day pair payday_day_1/payday_day_2 when both set (e.g. 5th + 20th, clamped per month), else the legacy two-pattern overload (payday_day_of_month: 1 → 1st + 15th, 15 → 15th + last-day-of-month). v5.3: both semimonthly forms route through expandSemimonthlyPaydays() with the business-day roll-back: a pay date on Saturday/Sunday pays the preceding Friday (US payroll ACH convention; field case — May 31 2026 is a Sunday, real deposits landed Fri May 29; holidays deliberately not modeled); biweekly/weekly derive the anchor from the primary income stream when user-confirmed or band ≥ medium. (2) inferred — no setting, or the setting couldn't compute. Next payday = the EARLIEST upcoming pay event across ALL eligible income streams (user-confirmed, or band ≥ medium; eligibility is category-gated to category IN (NULL, 'income') so recurring transfer-ins/refunds can never become "the payday"); else the today+14 placeholder with isFallback: true — consumers must never render the fallback as a real date (Until Payday becomes a "Set your payday" CTA). Amounts by unified band (confidence_bands.ts: low <0.5, medium 0.5–0.85, high ≥0.85-or-user-declared): declared Settings payday_amount (the TOTAL per paycheck) → always included (amountBasis: 'declared'); else v5.3 multi-account paycheck: when confirmed slices exist, predictedAmount = the SUM of every user-confirmed money-math-eligible income stream's resolved amount (resolveConfirmedPaycheckTotal() — the slices are one paycheck split by direct deposit, landing together; basis predicted); else high band → full predicted amount; medium band → p25 of the stream's observed deposits, labeled estimated_p25 (a $700–$1,300 gig earner is credited ~$775, not $0); low → null. User confirmation upgrades date AND amount (the old conf-0.3 pin that excluded a confirmed paycheck's amount is retired). Returns ResolvedPayday envelope: { nextPayday, predictedAmount, frequency, source, confidence, band, isFallback, amountBasis, daysUntilPayday, isPaydayToday, anchorDate } — band is a server-computed label; clients/Coach must never re-derive it from the raw score. Postgres date columns are normalized via toUserLocalDate() to avoid UTC-midnight-to-Eastern-evening shifts that previously slid May 2 bills into the May 1 window. How streams get confirmed (v5.3 multi-select): GET /paycheck-confirmations/candidates lists deposits ≥$500 in the last 60 days on depository accounts (each candidate carries confirmedStreamId for pre-selection; response includes confirmedStreams[] + the legacy currentlyConfirmed); POST /paycheck-confirmations {transactionIds[]} (legacy transactionId accepted) validates every pick is an inflow on a money-math-eligible account, groups picks per (bankAccountId, normalizedMerchantName) slice — several pay dates into one account become OBSERVATIONS of that slice (real occurrenceCount/average) — upserts each slice by the account-scoped identity key with user_confirmed=true, writes back transactions.recurring_stream_id, sets predictedNextDate from the semimonthly pattern (else +period), and clears user_confirmed from any income stream OUTSIDE the new set — the confirmed set IS the paycheck.

5SafeToSpendService

Backend passes redirect_uri = universal link URL to linkTokenCreate. iOS app must declare the matching domain in Tide.entitlements (applinks:<domain>) and the host must serve apple-app-site-association with this app's bundle + team ID. Without either, the Link session hangs at the OAuth return step.
Secret handling
Plaid access_token is stored AES-256 encrypted on bank_connections.access_token with serializeAs: null — never appears in any API response, never logged. All logs use redactForLogging(). client_id/secret live in backend env vars, never shipped to mobile.
Resilience
All Plaid calls routed through the BankDataProvider interface with circuit breaker (failureThreshold=5, resetTimeoutMs=30000, requestTimeoutMs=10000) and exponential backoff retry (3 attempts: 2s/4s/8s). Circuit open → fail fast; user sees "Connection paused, try again in 30s" rather than a cascade of errors.

POST /api/webhooks/plaid — HMAC-verified via Plaid JWKS (verification_key_id). Events handled: TRANSACTIONS.INITIAL_UPDATE, TRANSACTIONS.HISTORICAL_UPDATE, TRANSACTIONS.DEFAULT_UPDATE, TRANSACTIONS.TRANSACTIONS_REMOVED, ITEM.ERROR, ITEM.PENDING_EXPIRATION. Each maps to ProcessWebhookEventJob. Unsigned hits → 401.

The donut + category list on the Spending tab. Reads already-categorized transactions — category assignment itself happens upstream in Transaction Sync (see that flow for the Plaid Sync Category Resolution Priority). This flow is the spec for: windowing, filters (pending dedup, CC double-side, NON_SPENDING exclusion), aggregation into primaries + children, mobile drill-in flow with back-preserving breadcrumbs.
1Mobile App
User taps Spending tab — selects timeframe chip (Today / Last 7 Days / This Month)
Default timeframe='week'. Timezone auto-detected via Intl.DateTimeFormat().resolvedOptions().timeZone. Optional account filter (bankAccountIds array) selects which depository + credit accounts to include.
2Mobile App
Requests GET /insights/spending-by-category?timeframe=week&timezone=America/New_York
React Query hook useSpendingByCategory — cached in-memory with 60s staleTime. QueryKey includes timeframe, bankAccountIds, timezone — ensures different filters cache separately.
3Backend API
Validates request, resolves window in user timezone
spendingByCategoryValidator → InsightsController.spendingByCategory(). Computes windowStart/windowEnd:
• day = now.startOf('day') to now.endOf('day')
• week = rolling 7 days: now.minus({days:6}).startOf('day') to end-of-today
• month = now.startOf('month') to end-of-today
4InsightsController
Builds shared filter closure applyFilters(query)
transactions.user_id = user.id + transaction_date within window + is_pending = false (default) + optional bank_account_id IN (bankAccountIds). This closure is composed into the main aggregation query below.
5Lucid ORM
Detail aggregation — transactions × categories × parent categories
One query with two LEFT JOINs:
db.from('transactions') .leftJoin('categories as c', 'transactions.category_id', 'c.id') .leftJoin('categories as p', 'c.parent_code', 'p.code')
SELECT c.id, c.code, c.name, c.parent_code, p.name as primaryName, p.icon, p.color, SUM(amount), COUNT(*). GROUP BY all selected columns.
~20-50ms
6Filter layer 1
excludeSupersededPending() — pending dedup
Applied via shared helper from transaction_filters.ts. Two conditions (NOT …): (a) Plaid's pending_transaction_id points to this row's plaid_transaction_id, OR (b) heuristic: same user_id + bank_account_id + merchant_id + amount + date within 7 days AND this row is pending with a posted sibling. The heuristic covers Plaid sandbox where the FK is rarely set.
7Filter layer 2
excludeCreditCardSideOfCcPayment() — CC payment double-side filter
When a credit card payment happens from checking, Plaid returns 2 rows (one per account), both tagged LOAN_PAYMENTS_CREDIT_CARD_PAYMENT. In spending contexts we suppress the credit-card-account side so the payment only counts once. Applied unconditionally in this endpoint; applied in /transactions only when categoryId or parentCategoryCode is set AND bankAccountId is not (so per-account views still show both sides).
8InsightsController
Partition rows: spending / excluded / uncategorized
NON_SPENDING_PRIMARIES = ['INCOME', 'TRANSFER_IN', 'TRANSFER_OUT']. Rows whose parent_code is in this set go to the excluded bucket (surfaced separately in the footer). Rows with null category_id go to uncategorized. Everything else is "spending."
9InsightsController
Group spending rows by primary code → primaryMap
For each spending row, accumulate into the primary bucket: sum totalAmount, sum transactionCount, append to children[] (each child has its own categoryId, code, name, amount, count). Primary metadata (icon, color, name) comes from the p.* join columns. pctOfTotal = Math.round((primary.amount / totalSpent) × 1000) / 10 (1 decimal).
10Backend API
Returns SpendingByCategoryResponse JSON
{ timeframe, windowStart, windowEnd, timezone, totalSpent, transactionCount, primaries: [{ primaryCode, name, icon, color, totalAmount, transactionCount, pctOfTotal, children: [...] }], excluded: { income, transfersIn, transfersOut }, uncategorized: { totalAmount, transactionCount } }. Primaries sorted by totalAmount desc; children within each primary also sorted desc.
11Mobile App
Renders donut chart + primary rows + footer
CategoryDonut component (animated slices by color). Each primary row: icon in a colored circle, name, txn count · formatPercent(pctOfTotal), totalAmount, chevron. Tiny percentages render as <0.1% not 0%. Footer: "Not counted in spending" with collapsed Transfers (tappable) + Uncategorized (tappable info icon). Income and Transfers-in are hidden — not spending-adjacent.
12Drill-in
Tap primary → drill-down OR single-child shortcut
If primary.children.length === 1, navigate direct to /(tabs)/all-transactions with params {categoryId, categoryName, startDate, endDate, timeframeLabel, categoryColor, categoryIcon}. Otherwise push to /(tabs)/spending/[primaryCode] drill-down. Drill-down passes timeframe + accountIds through params so numbers match parent. Tapping a child passes the SAME params plus a breadcrumb fromPrimaryCode / fromTimeframe / fromAccountIds so the Back button on all-transactions returns to the exact drill-down page (not Home, not Spending index).
13Mobile App
Transactions drill-in — rich context header
Top of all-transactions: category icon (colored circle), name, total (client-side sum over loaded pages), transaction count, date range like Apr 13 – Apr 19, × to clear. useInfiniteTransactions sends categoryId + startDate + endDate to /transactions, which applies the same pending dedup + CC double-side filters. Context header auto-hides during search.
Total end-to-end: ~100–200ms
SPEC — SPENDING INSIGHTS
Timeframes (MVP)
day · today only · week · rolling last 7 days (not calendar week) · month · calendar month-to-date (1st → today). Label shown to user: "Today" / "Last 7 Days" / "This Month" — week is honest about the rolling window.
Category taxonomy
Primaries come from Plaid PFC (16 categories) plus two Tide extensions: SOFTWARE_AND_TECH (single catch-all subcategory SOFTWARE_AND_TECH_ALL) and SUBSCRIPTIONS (entertainment subs). Reparented Plaid codes: ENTERTAINMENT_MUSIC_AND_AUDIO + ENTERTAINMENT_TV_AND_MOVIES → SUBSCRIPTIONS; GENERAL_SERVICES_INSURANCE → TRANSFER_OUT (insurance is investment-like, not discretionary spending).
Seeded via category_seeder.ts + plaid_pfc_taxonomy.csv. NAME_OVERRIDES map handles display names for reparented codes.
Filters — applied in order
1. Pending dedup (excludeSupersededPending) — hides pending rows that have a posted sibling. Primary rule: pending_transaction_id FK; heuristic fallback: user + account + merchant + amount within 7 days.
2. CC double-side (excludeCreditCardSideOfCcPayment) — suppresses the credit-card-account side of LOAN_PAYMENTS_CREDIT_CARD_PAYMENT. Applied unconditionally in the insights query (per-account semantics don't apply here since this is aggregate spending).
3. NON_SPENDING partition — rows with parent_code in [INCOME, TRANSFER_IN, TRANSFER_OUT] land in the excluded bucket and don't count toward totalSpent.
Footer behavior (what's "Not counted in spending")
Hidden entirely: Income, Transfers-in (not spending-adjacent).
Shown + tappable: Transfers-out (tap → drills into the Transfer Out primary via parentCategoryCode=TRANSFER_OUT) and Uncategorized.
Both rows have an ⓘ affordance opening an explanation sheet.
Related flows (upstream)
Category assignment to each transaction row happens at Transaction Sync time — see Transaction Sync Flow for the Plaid Sync Category Resolution Priority (user override → AI cache → Plaid detailed). Spending Insights just READS transactions.category_id.

MVP+ — dev-bypassed during the MVP sprint. Passwordless SMS OTP via AWS Cognito. User gets JWT tokens stored in SecureStore. Dev mode uses a hard-coded bypass user (ID 53) so Claude/dev work is not blocked by auth during the sprint.

3AWS Cognito
Sends SMS OTP via SNS

4User

Keychain (iOS) / Keystore (Android). Auto-refresh on 401 using refresh token. 401 interceptor skips logout() in dev-bypass mode to prevent auth cache wipe.

Evening Reflection Session Flow (MVP+)
MVP+ — Backend intact, frontend entry points removed (UI unreachable). Daily cron checks for untagged transactions, sends reminder, user tags transactions, session completes. All UI entry points removed (Home, the Settings screen — now under the Profile tab — the tab bar, and the former Progress tab, itself removed 2026-06-10 with the challenges feature) — legacy route files (evening-reflection.tsx, reflection-history.tsx) still exist but are not registered in the tab navigator and nothing navigates to them. Backend files preserved for MVP+ reactivation.
1Cron Scheduler
Triggers evening reflection check based on user settings
BullMQ repeatable job on evening-reflections queue. Queries reflection_settings for enabled users matching reminder time window.
2Worker
Checks for untagged transactions today
Queries today's transactions that have no transaction_reflections record. If none found, skips user.
~20-50ms
3Worker
Creates reflection session and sends FCM reminder
Creates reflection_sessions record with status pending. Sends push notification: "You have X transactions to reflect on today."
4User
Opens app and tags each transaction
Swipe UI for each transaction: worth-it, regret, or neutral. Optional note per transaction. Creates transaction_reflections records.
5Backend API
Marks session complete
Updates reflection_sessions.status to complete and sets completed_at. All transactions tagged.
6Backend API
Session recorded — no streak update
This step previously incremented a reflection streak; the streak feature (and the user_streaks / streak_milestones tables) was removed 2026-06-11, so reactivating reflections would track completion via reflection_sessions alone.
