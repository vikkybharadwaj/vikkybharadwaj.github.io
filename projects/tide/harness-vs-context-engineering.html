Harness vs. Context Engineering

Decoding Mike Piccolo's "How to build your own agent harness" and Anthropic's context-engineering playbook — and pinning down exactly where Tide sits between them. A quick card to re-read whenever the two terms blur together.

⬡ REFERENCE  This is an explainer, not a spec — it doesn't change with the code. The one idea to keep: a harness is the runtime that drives an agent turn; context is what the model sees on that turn. Tide doesn't build a harness (Claude Code is the harness) — Tide's leverage is context engineering + the operating-system layer on top of it. See the live Operating System map for what that layer actually contains.
⚙ The plumbing

Harness engineering

Building / owning the runtime that drives an agent turn.

What it is
The loop, tool dispatch, policy checks, approvals, streaming, session persistence, compaction, tracing — the ~15 jobs below.
The question it answers
"How does a turn physically execute, and can I swap any piece without a rewrite?"
Who owns it for Tide
Claude Code — you don't build this, and shouldn't.
Failure mode it prevents
Vendor lock-in: "the policy engine won't extend the way I need."
◍ The tokens

Context engineering

Curating what tokens the model sees on each turn.

What it is
System prompt, memory, retrieved docs, tool schemas, recent history, the task — kept to the smallest high-signal set.
The question it answers
"What's the smallest set of high-signal tokens most likely to produce the behavior I want?"
Who owns it for Tide
You. This is where ~100% of your leverage is.
Failure mode it prevents
Context rot — as the window fills, recall + reasoning degrade (attention is finite, n² in tokens).
The punchline. The iii article tells you what a harness does. Anthropic's playbook tells you how to feed the harness well. For a solo fintech app on Claude Code, harness engineering is a solved/borrowed problem — context engineering is the job.
1

What the article actually says

Mike Piccolo (founder of iii, an agent-infrastructure company) makes one core argument. Read it as a checklist + a philosophy, not a "go build this" — it's largely a pitch for iii's own substrate, aimed at teams building agent platforms.

"A harness is not one thing you install — it's ~15 separate jobs bundled together. Frameworks (LangChain, LangGraph, CrewAI, the SDKs) ship all 15 as one welded block. That's the mistake. You should be able to swap any one piece without touching the rest."

  • A harness = runtime plumbing. It takes your message, picks a model, resolves credentials, assembles the system prompt, streams tokens, runs the tools the model asks for, checks each call against a policy, pauses for human approval, tracks spend, runs before/after hooks, persists the session, compacts history when the window fills, and emits a trace to debug it.
  • Workers, not a monolith. iii's bet: make each job an independent "worker" that talks to a shared engine over one primitive — a trigger() call. "Build your own harness" stops meaning "fork a framework" and starts meaning "swap a few workers."
  • Thin vs. thick is a slider, not a fork in the road. A thin harness is ~4 workers (orchestrator + provider + credentials + minimal meta-worker — "trust the model"). A thick one adds policy, approvals, budgets, audit, Slack approvals. Moving between them is a config change, not a rewrite.
  • Observable by construction. One OpenTelemetry trace threads through every worker, so a turn is debuggable end-to-end.
The honest caveat for Tide: you are not building an agent platform — you're a consumer of a harness, and Claude Code is it. The article's value is (a) the cleanest checklist of "what a harness must do," which shows which jobs Claude Code already handles for you, and (b) its decomposition philosophy — make every layer independently replaceable and observable — which you can apply inside your repo without touching agent plumbing.
2

Context engineering — Anthropic's playbook

The other half. Anthropic frames context engineering as the natural evolution of prompt engineering: prompt engineering writes one good instruction; context engineering manages the entire evolving information state across a long multi-turn session.

  • Smallest high-signal token set. Context is a finite resource with diminishing returns. Every token added depletes the model's "attention budget" — find the smallest set of high-signal tokens that maximizes the desired outcome.
  • System prompts at the "right altitude." Specific enough to guide, flexible enough to leave room for judgment — neither brittle hardcoded if/else nor vague platitudes.
  • Tools: quality over quantity. "If a human engineer can't say which tool to use, the agent can't either." Self-contained, unambiguous, token-efficient returns.
  • Just-in-time / progressive disclosure. Keep lightweight references (file paths, queries) and load the actual content only when needed — like a human using a filing system instead of memorizing everything.
  • Sub-agents for context isolation. A sub-agent burns tens of thousands of tokens exploring, then returns a 1–2k-token distilled summary, keeping the main window clean.
  • Memory / note-taking outside the window. A NOTES.md or to-do list persisted on disk gives durable memory across long tasks and across compaction.
  • Compaction near the limit. Summarize, preserving architectural decisions + unresolved bugs and discarding redundant tool output.
  • Context rot is real. Transformer attention creates n² pairwise relationships; as context grows, recall and long-range reasoning measurably degrade. Treat context as precious even as models improve.
