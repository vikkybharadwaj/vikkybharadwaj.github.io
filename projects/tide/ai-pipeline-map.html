AI Pipeline

Multi-agent architecture · ← Hub

Stage 1 — Input

User Message

User sends natural language query via mobile chat UI. Example: "How much did I spend on dining this month?"

Stage 2 — Classification (DISABLED)

Intent Classifier (Haiku 4.5)

Currently turned OFF — chats_controller.ts sets const intentPromise = Promise.resolve('unknown'). A per-message Haiku call competed with the chat stream for Bedrock quota and triggered throttling, so the stage is stubbed out (re-enable once AWS quota is raised). When live, it would classify query intent on AWS Bedrock; today every turn is routed to the Coach with all 10 tools regardless of intent.

disabled (was <500ms target)
Stage 3 — Agent

Tide Coach Agent (Sonnet 4.6)

Primary AI financial coach. Has all 10 tools available every turn (intent routing is disabled — see Stage 2) and lets the model pick which to call. Generates personalized financial advice with full conversation context.

First token <2s
Stage 4 — Tool Execution

Backend API (Read-Only DB)

Agent's tool calls execute against PostgreSQL via Backend API. Uses dedicated read-only connection. Bouncer policies enforced.

30-200ms per query
Stage 5 — Streaming

SSE Response via XMLHttpRequest

Tide Coach generates natural language response streamed via SSE using XMLHttpRequest (not fetch — RN's fetch lacks response.body). Tokens appear in real-time. Partial responses saved even when streaming errors occur.

SSE via XHR
Stage 6 — Persistence (Async + Fallback)

Chat Persistence + Coaching History

Both user and assistant messages persisted with intent, model, and toolsUsed metadata. toolsUsed jsonb column uses JSON.stringify prepare/consume serializers. BullMQ primary with synchronous DB fallback if dispatch fails. Error path: partial AI responses saved even on streaming errors. Content AES-256 encrypted.

BullMQ async · sync fallback · 30d retention

Tool reference

TOOL 1

query_user_profile

Who the user is: name and how long they have used Tide.

When the Coach uses it
Personalising a greeting, or questions about the account itself.
Inputs

No inputs. The tool always works on the signed-in user.

Logic, step by step
  1. Loads the user and profile on the read-only connection (tool_executor.ts queryUserProfile).
  2. Computes account age in days from users.created_at.
Output
  • name, accountCreated, accountAgeDays
Known limits
  • No phone, address or other contact PII by design.
TOOL 2

query_bank_accounts

Every linked, active account with its balances.

When the Coach uses it
"What is my balance", net-worth style questions, or anything naming a specific account.
Inputs

No inputs. The tool always works on the signed-in user.

Logic, step by step
  1. Reads bank_accounts where is_active, with the owning bank_connection (queryBankAccounts).
  2. Returns the official account name when the bank provides one, otherwise the display name.
Output
  • per account: id, name, accountType (depository / credit / loan), accountSubtype, institutionName, currentBalance, availableBalance, currency
Known limits
  • For credit and loan accounts currentBalance is what is OWED, not cash. The Coach has to read accountType to tell them apart.
  • Balances are as of the last Plaid sync, not live.
  • No asset values (home, car), so it cannot support a true net-worth figure.
TOOL 3

query_transactions

Raw transaction lookup with filters.

When the Coach uses it
A specific merchant, date range, account or amount ("How much at Amazon lately?").
Inputs
InputTypeMeaning
bankAccountIdnumberFilter to a specific bank account ID (from query_bank_accounts). Use this when the user asks about a specific account or bank.
startDatestringISO date YYYY-MM-DD
endDatestringISO date YYYY-MM-DD
categoryIdnumber
merchantNamestring
minAmountnumber
maxAmountnumber
transactionTypedebit | credit
limitnumberMax results, default 50
Logic, step by step
  1. Reads transactions for the user, newest first, with merchant, category and account (queryTransactions).
  2. Applies whichever filters are given: account id, start/end date, category id, merchant name (case-insensitive contains), min/max amount, debit/credit.
  3. Returns at most limit rows: default 50, never more than 100.
Output
  • per transaction: id, amount, description, transactionDate, transactionType, isPending, merchant, category, accountName, institution
Known limits
  • Capped at 50 rows by default (100 max) with NO total count, so a "total" summed from the list can silently miss older rows.
  • Includes PENDING rows. A pending charge and its posted twin can both appear, which reads like a double charge. The Spending tab de-duplicates these; this tool does not.
  • Filtering by category needs a numeric categoryId, and no tool lists category ids.
TOOL 4

query_bills_predictions

Upcoming recurring bills and subscriptions.

When the Coach uses it
"What bills are coming up?", "When is my mortgage due?"
Inputs
InputTypeMeaning
daysAheadnumberHow many days ahead to look, default 30
unpaidOnly ignored by the codebooleanOnly return unpaid bills, default true
Logic, step by step
  1. Reads active recurring_streams of type bill or subscription whose next predicted date falls between today and today + daysAhead (default 30) (queryBillsPredictions).
  2. Drops streams billed to a credit card (isMoneyMathEligible): those charges are paid through the card bill.
  3. Returns them in date order.
Output
  • per bill: id, predictedAmount, predictedDate, confidence (0–1), merchant, recurrencePattern, isPaid (always false)
Known limits
  • Finding #1. Does NOT include credit-card payments due. Home's Recurring Expenses adds those from Safe to Spend, so the Coach's answer can miss most of what is actually due.
  • unpaidOnly is declared but ignored, and isPaid is hard-coded false.
  • The date window uses the server clock, not the user's timezone.
TOOL 5

query_payday_predictions

When the next paycheck lands and how much, plus other expected income.

When the Coach uses it
"When do I get paid?", "Will I make it to payday?"
Inputs
InputTypeMeaning
daysAheadnumberHow many days ahead to look, default 30
Logic, step by step
  1. Resolves the authoritative next payday with resolvePayday (the same helper Home uses): the user's payday setting wins on cadence, the income stream wins on amount.
  2. Separately lists active income streams due within daysAhead (default 30), excluding transfer-ins, refunds and card "payment received" credits.
Output
  • resolved: nextPayday, predictedAmount, frequency, source, confidence, band (low/medium/high), isFallback, amountBasis, daysUntilPayday, isPaydayToday
  • upcoming[]: id, source, predictedAmount, predictedDate, confidence, frequency
Must match
Home payday chip. Both read the same code.
Known limits
  • A low-confidence or fallback payday is an ESTIMATE. The Coach must not state it as fact (red line 10).
  • The upcoming[] window uses the server clock, not the user's timezone.
TOOL 6

calculate_safe_to_spend

How much the user can spend: the same Safe to Spend engine that powers Home.

When the Coach uses it
Affordability ("Can I afford…?"), "How much can I spend this week?", "Will I make it to payday?"
Inputs

No inputs. The tool always works on the signed-in user.

Logic, step by step
  1. Calls computeSafeToSpend (safe_to_spend_service.ts) in the user's timezone, the single engine shared with GET /predictions/safe-to-spend.
  2. The engine projects the checking balance day by day: L(d) = cash + income landing on or before d − obligations on or before d. Obligations are bills, loans, card payments due, essentials and estimated everyday "habits".
  3. Horizon = whichever is later: the day before payday, or month end.
  4. Daily pace = the lowest L(d) ÷ (d+1) across the horizon, so spending at that pace never dips below zero on any day.
  5. Each window (today, this week, until payday, this month) = pace × the days in that window. If the pace is negative (a shortfall), every window equals the deficit instead.
  6. projectSafeToSpendForCoach reshapes the result so every number Home shows is reachable from one tool call.
Output
  • today / thisWeek / untilPayday / thisMonth: amount, daysInWindow, perDayInWindow, moneyOut {billsUtilsSubs, loans, plannedSavings, ccDue, essentials, habits, total}, bills[], income[]
  • dailyBudget, daysUntilPayday, isPaydayToday, nextPayday, spendableBalance
  • floor {date, value, bindingBill}, shortfall {isShortfall, shortfallAmount, earliestShortfallDate}
  • ccObligations[] per card {amountDue, basis, dueDate, minimumPayment, purchaseApr, totalBalance}, ccNextCycleWarning, creditCardDebt (display only)
  • essentials, typicalDiscretionary, accountsIncluded, setAsideAccounts, loansExcluded, lastSyncedAt
Must match
Home Safe to Spend card. Both read the same code.
Known limits
  • Finding #3. When payday and month end fall on the same day, the horizon is ONE day, so the daily pace becomes the whole balance and multi-day windows multiply it (30 Sep 2026: today $17,365.85, this week $86,829.25).
  • Finding #4. Its description, which the Coach reads, still describes v5.1 ("the global floor caps every window; This Week can never exceed This Month"). The engine is v5.5 and no longer caps, so the Coach is told a rule that is no longer true.
  • A card payment is subtracted only once its due date falls inside the window, so "already accounted for" is wrong for today's figure when the payment is due later.
  • creditCardDebt is the full revolving balance for display. It is NOT subtracted; only the statement amount due is.
TOOL 7

get_spending_by_category

True spending by category: the same numbers as the Spending tab donut.

When the Coach uses it
"What did I spend on food this month?", "Where did my money go?"
Inputs
InputTypeMeaning
timeframeday | week | monthSpending-tab window in the user's timezone: day = today, week = last 7 days rolling, month = current calendar month to date. Default month. Ignored when startDate/endDate are given.
startDatestringISO date YYYY-MM-DD — custom range start (overrides timeframe)
endDatestringISO date YYYY-MM-DD — custom range end
Logic, step by step
  1. Resolves the window in the user's timezone: today, last 7 days rolling, or month to date (default). A custom start/end overrides it; an end without a start looks back 30 days (getSpendingByCategory).
  2. Fetches posted rows only (pending excluded) with the Spending tab's shared SQL (fetchSpendingDetailRows).
  3. projectSpendingForCoach partitions income, transfers and card-bill payments out of spending, nets refunds per category, and sums positive categories into totalSpent.
Output
  • window {timeframe, startDate, endDate, timezone}, totalSpent, transactionCount
  • categories[] {category, total, pctOfTotal, transactionCount, subcategories[]}
  • excluded {income, transfersIn, transfersOut, ccPayments}, uncategorized {total, transactionCount}
Must match
Spending tab donut. Both read the same code.
Known limits
  • Month to date is a partial month. Comparing it with a full previous month needs saying so.
  • A large NEGATIVE uncategorized bucket is money coming in (often payroll or a transfer the categoriser missed), not refunds and not "hidden spending".
TOOL 8

get_financial_insights

Four analyses in one tool: monthly trend, largest expenses, recurring charges, anomalies.

When the Coach uses it
Trends ("Am I spending more than usual?"), biggest purchases, "What am I subscribed to?", "Anything weird?"
Inputs
InputTypeMeaning
insightTypespending_trends | largest_expenses | recurring_charges | anomalies
monthsnumberHow many months of data to analyze, default 3
Logic, step by step
  1. insightType picks the analysis (default spending_trends). months is capped at 12, default 3 (getFinancialInsights).
  2. spending_trends: the same true-spending monthly totals as the Home chart, calendar months in the user's timezone.
  3. largest_expenses: the 10 biggest DEBIT rows in the last N months, straight from transactions.
  4. recurring_charges: every active recurring stream, most frequent first.
  5. anomalies: per category, the mean and standard deviation of debits over N months. Returns up to 10 debits more than 2 standard deviations above their category mean.
Output
  • spending_trends: months[] {month, total, transactionCount}
  • largest_expenses / anomalies: transactions[] {amount, description, date, merchant, category}
  • recurring_charges: merchants[] {merchant, transactionCount, averageAmount, streamType, frequency, confidence, predictedNextDate, predictedNextAmount}
Must match
Home spending chart (spending_trends only). Both read the same code.
Known limits
  • largest_expenses uses raw debits, so transfers between your own accounts and card-bill payments rank as "expenses".
  • anomalies counts pending and posted copies separately and does not exclude transfers, so a pending/posted pair can look like a duplicate charge.
  • recurring_charges ignores months and includes income and card-billed streams as well as bills.

Agent Memory Model (Tool-Based Context)

The agent pulls context on demand via tools — no pre-loaded financial profile in prompts. Scales with data growth, token-efficient.

TIER 1

Session Context

Current chat thread built into the conversation. Resets between sessions. Provides immediate conversational continuity.

TIER 2

Financial Data

Accounts, transactions, predictions, spending, reflections (MVP+). Agent pulls on demand via tools 1-8, 10. Data lives in Postgres, fetched only when relevant.

TIER 3

Coaching History

Past recommendations + user responses + outcomes. Via tool 9 (query_coaching_history). Enables: "I suggested canceling Hulu last month — did you follow through?"

Plaid Sync — Category Resolution Priority

Canonical spec in Transaction Sync Flow (where it executes at sync time). Mirrored here for the AI-first view since Tier 2 runs Claude Haiku.

TIER 1

User Merchant Rule

merchant_category_overrides row — written when the user recategorizes a transaction and picks "Always for <merchant>" (PATCH /transactions/:id with applyToMerchant: true). categorySource='rule'. Direct per-transaction edits set categorySource='user' on the row itself, which sync never clobbers (the guard above all tiers).

TIER 2

Merchant AI Cache

merchants.ai_category_id — set by Claude Haiku on a prior sync when Plaid's code was ambiguous. categorySource='ai'. One Haiku call per unique merchant, reused forever.

TIER 3

Plaid Detailed Code

Plaid's native PFC classification. Used when no user override and no AI cache. categorySource='plaid'. Handles confident cases (coffee, gas, groceries) with no AI cost.
